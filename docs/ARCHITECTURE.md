# معماری

```text
رابط Flutter
    │
    ├── Work store / audit / memory / checkpoints (محلی)
    │
    └── AgentEngine
          ├── Policy → تأیید عملیات مؤثر
          ├── ToolRegistry → فایل، فرمان، git، مرورگر، PDF و DOCX
          └── FailoverModelAdapter
                 └── ByokModelAdapter ──HTTPS──> ارائه‌دهندهٔ انتخابی کاربر
                                      (با پراکسی اختیاریِ تنظیم‌شده توسط کاربر)
```

هیچ مسیر حساب، اشتراک، پرداخت، relay یا مدل مدیریت‌شده در runtime وجود ندارد.
هر مدل قابل اجرا باید از `ByokStore` به یک پیکربندی محلی و یک راز قابل
رمزگشایی برسد.

## تاریخچه و failover

`ByokConversationState` مالک تاریخچهٔ مستقل از قالب است. ورودی تنها پس از
پاسخ موفق commit می‌شود؛ بنابراین retry ورودی تکراری نمی‌سازد. هنگام تغییر
ارائه‌دهنده، همان exchangeها به قالب OpenAI-compatible یا Anthropic تبدیل
می‌شوند و ترتیب assistant/tool حفظ می‌شود.

## لغو و منابع

هر درخواست یک `AbortableRequest` دارد. توقف کار سیگنال لغو را به انتقال HTTP
فعال می‌رساند. تعویض مدل، آداپتور قبلی را dispose می‌کند و بستن موتور کلاینت
باقی‌مانده را می‌بندد.

## مرزها

- رازها: DPAPI ویندوز؛ بدون fallback متن ساده.
- شبکه: endpointهای شناخته‌شده با HTTPS؛ HTTP سفارشی فقط روی loopback.
- فایل و فرمان: عملیات مؤثر نیازمند تصمیم policy است؛ shell همیشه تأیید
  مستقل می‌خواهد و sandbox سیستم‌عامل نیست.
- محتوای بیرونی: نتیجهٔ ابزار با نقش ساختاریافتهٔ `tool` بازگردانده می‌شود.
- انتشار: تست boundary کل فایل‌های متنی مخزن را برای شناسه‌های زیرساختی،
  credentialهای شناخته‌شده و IPv4 عمومی بررسی می‌کند.
